# Changelog

## 2026-08-03 (iMessage checkout link never appeared — Linq Payments API instead of Prava)
- **Root cause (the main bug):** The iMessage webhook selection branch (`/api/linq/webhook`) called the **Linq Payments API** (`api.linqapp.com/.../payments`) and read guessed fields (`attach_url` / `approval_url`) when the user replied "1/2/3" — it **never called Prava**. That's the §7 anti-pattern from `tasks/lessons.md` (don't guess an API, check it). Meanwhile the web app worked because `/api/pay` → `createSession()` returns a real Prava `iframe_url`. The iMessage path bypassed the integration we'd already proved out, then blamed "prava sandbox is being weird" for a call Prava never received.
- **Fix:** the webhook now calls `createSession()` directly — same code path as the web app — and sends the returned `session.iframe_url` as an iMessage Rich Link part (`{ type: "link" }`). The `iframe_url` *is* the Prava hosted checkout. Phone-derived `userId` (`imessage_<number>`) stands in for Supabase auth so Prava recognizes returning iMessage users and surfaces their saved card; `merchantUrl` is pinned to the real brand site (not `prava.space`) so the virtual card stays scoped to the actual checkout target — the Step 5 gating requirement.
- **"Always top 3" framing fix:** Saul's system prompt literally said *"mention the other two as backup"* and *"show all three"* — priming him to talk in threes even when a brand had only two products. The `matches.slice(0, limit)` itself was safe (can't pad a 2-product brand to 3 rows); the bug was the prompt framing. Rewrote to frame around however many came back, with an explicit "never reference a product you weren't given."
- **Silent 1/2/3 fall-through bug:** `["1","2","3"].includes()` + `pendingRecommendations[idx]` meant that for a 2-product brand, replying "3" gave `selected === undefined`, the `if (selected)` check silently failed, and "3" fell through to the LLM as a normal message. Now validates against the actual rec count and replies "i only sent you N options" instead.
- **Persistence (the in-memory Map problem):** `pendingRecommendations` lived in a serverless-memory `Map`, which doesn't survive across Vercel instances — so a reply could hit a cold instance that didn't have the recommendations and silently do nothing. Replaced with a `imessage_convos` table (keyed by sender phone, mirrors the `checkout_otp_handoff` pattern). The webhook now loads/saves convo state per message; recommendations persist across instances and restarts.
- **Completion callback (iMessage has none):** Once the Prava link opens in the user's browser sheet, the webhook had no way to know checkout completed, so it couldn't `reportStatus()` — sessions sat in `awaiting_result` on the dashboard. Added a Vercel cron (`/api/linq/cron`) that polls `payment-result` for open iMessage sessions and reports the **real** status (DECLINED on merchant decline, never auto-APPROVE — per the 2026-08-03 premature-APPROVED lesson). On terminal status it sends Saul a confirmation text so the iMessage user gets a receipt.

## 2026-08-03 (Dashboard showed Success — premature APPROVED was clobbering DECLINED)
- **Root cause of the dashboard contradiction (the real bug behind "honesty fix B"):** Two `report-status` calls fired per checkout, in the wrong order. The payment modal (`prava-payment-modal.tsx`) and the WebKit poll path (`chat-client.tsx`) both reported `APPROVED` the instant the Prava *session* completed (card token issued) — *before* the autonomous checkout even ran. Per the Prava docs: *"Reporting a one-time mandate charge as APPROVED consumes the mandate."* Once APPROVED landed, the transaction was finalized as `completed`. My checkout route's later `DECLINED` report then hit `INVALID_STATE: no transaction awaiting result` (HTTP 400) and was **silently rejected**. So every transaction showed Success/Completed on the dashboard — not because Prava ignored us, but because APPROVED got there first and sealed it. The `http=200 status=confirmed` in the logs was the modal's APPROVED, not my DECLINED. I misread it.
- **Fix:** removed the premature APPROVED report from both call sites (modal + WebKit poll). The autonomous checkout route now owns the ONLY `report-status` call, reporting DECLINED (the true sandbox outcome: the one-time test card is declined by the merchant). The route's catch block also reports DECLINED on crash, so the transaction never sits in `awaiting_result` forever.
- **Bonus:** the OTP handoff `.single()` bug ("Cannot coerce the result to a single JSON object", PGRP116) is fixed — switched to `.select()` + length check, returns a retryable 409; the client auto-retries once. The card-iframe drill `e.url is not a function` crash is fixed — the v3 Frame object only exposes `.evaluate()`, not `.url()`. Phone edit added to the avatar menu.

## 2026-08-02 (Shopflo card step cracked — pointer events + Cashfree iframes)
- **Root cause of the "card form won't expand" bug found via live probe:** The "Debit/Credit cards" option on Shopflo is a `MethodCard.tsx` row that binds to `onPointerDown`, not `onClick`. `el.click()` (synthetic click event) was invisible to its handler — the form never expanded. The fix: dispatch the full native tap sequence (`pointerover → pointerdown → mousedown → pointerup → mouseup → click`) from inside `frame.evaluate()`. One tap reliably opens the form.
- **Card fields live in nested Cashfree payment-gateway iframes** (not Razorpay — confirmed via `cashfreelogo.cashfree.com` in the brand-logo `<img>` srcs). The container `#flo__payments__CARD` populates with separate PCI-compliant iframes for card-number / expiry / cvv. `shopfloCardStep` now: taps the MethodCard → polls up to 8s for the iframes to appear → drills into every child frame via `page.frames()` and fills each card field there (not just the Shopflo frame).
- **Full Shopflo flow now mapped end-to-end:** `phone → OTP gate → address auto-fetch → tap MethodCard → Cashfree iframes render in #flo__payments__CARD → fill card fields in each iframe → submit`. The OTP-pause + live-status UI + phone collection already shipped today; this was the last unmapped link.
- **Honest reporting preserved:** if the Cashfree iframes are unreachable from our evaluate context (deeper cross-origin isolation), the route still reports DECLINED as the expected sandbox outcome but logs it plainly instead of faking a filled-form success.

## 2026-08-02 (Honesty fixes — fake fallback + silent report-status)
- **Killed the fabricated "Test card declined" message (Fix A):** `chat-client.tsx` was rendering a hardcoded `"Test card declined"` string whenever `merchantError` was empty — which dressed up a total automation failure (card fields never filled) as a win. Now reports honestly: only claims a clean decline when `isDeclined === true`; otherwise says plainly that the merchant page never confirmed a decline and the card fields may not have filled. Root cause surfaced via Cannazo logs showing `Merchant response: { errorMessage: '', isDeclined: false }` followed by a UI claiming success.
- **Made `reportStatus` loud and verifiable (Fix B):** `prava.ts:reportStatus` was fire-and-forget — no `res.ok` check, no body read, no logging, wrapped in `.catch(() => {})` at the caller. We were reporting DECLINED to Prava but the dashboard showed Success/Completed/Order completed, meaning the report never landed (or Prava auto-resolved). Now: checks `res.ok`, reads + logs the full response to Vercel logs (HTTP status, Prava `status`, `txn_status`, `visa_confirmation`), throws on non-2xx, and returns a typed `ReportStatusResult` (`{ confirmed, txnStatus, visaConfirmation, raw }`).
- **Surfaced the real report result in the UI (Fix C):** `checkout/automate` route now returns `reportConfirmed` + `visaConfirmation` (and `reportError` on the error path) instead of the unconditional `statusReported: "DECLINED"`. The UI now shows: "⚠️ Prava did NOT confirm the DECLINED report. The dashboard may show a different status — check it." when `reportConfirmed === false`, or a Visa-FAILURE warning when applicable. This is the receipt for the dashboard contradiction.
- **Platform detection across 12 brands:** 7 of 10 reachable sites are Shopify (The Trost, Moon Impact, Cannazo, Qurist, Hebe, ANDYOU, Cannavedic); AarogyaCBD is WooCommerce; Kushiva + ItsHemp are custom/unknown. Cannazo is Shopify but renders card fields in an unreachable payment iframe — so the card-fill issue is merchant-specific, not platform-specific. The Trost + Moon Impact are the safest demo picks.
